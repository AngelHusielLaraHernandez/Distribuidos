\section{Objetivo}
Comprender cómo se mantiene el orden lógico de eventos en sistemas distribuidos mediante el uso de relojes vectoriales.

\section{Planteamiento del escenario:}
Para el escenario, se tomo base las aplicaciones de reparto de comida
donde en este punto tomamos como referencia una arquitectura de microservicios,
esto mas precisamente cuando un cliente hace una orden, en nuestro caso tomamos como referencia
al restaurante Carls jr, donde tomamos como pedido la hamburgesa Famose star, esto lo tomamos
desde que el usuario selecciona la hamburguesa hasta que el sistema manda la notificación final de entrega, 
ahora bien, tomamos a los procesos como las responsabilidades.

Para esto, todo comienza en el Proceso 1 que es como tal la Aplicación Cliente, este proceso
simula la UI de usuario propiamente, donde como tal el evento interno es agregar la comida al carrito de compras 
y el monto a pagar, depsues de esto, una vez que la orden está lista, 
el Proceso 1 envía una solicitud de cobro mediante un mensaje punto a punto al Proceso 2 que este sera nuestro 
movimiento de Pago (donde se verifica si la tarjeta es verdadaera y tiene fondos), 
transmitiendo su reloj vectorial inicial para emepzar la sincronización temporal del sistema.

Despues de esto, al recibir la solicitud, el Proceso 2 actualiza su reloj local 
y ejecuta un evento interno que es el de validar los datos de la tarjeta y procesar la propia transeaccion,
despues tras aprobar el pago, este proceso se comunica con el Proceso 3 que en este punto lo estamos simulando 
como si fuera la aplicacion que se tiene en la cocina del Restaurante, 
enviándole la confirmación de fondos aprobados y los detalles de la misma orden, en este caso que tipo de hambrugesa 
va a desear el cliente, esto lo que hace es que garantiza un orden lógico, donde como tal
el restaurante no comenzará a cocinar sin que el pago haya sido exitoso.

Posteriormente, el Proceso 3 registra un evento interno simulando la preparación 
y el empaquetado de la orden, de hecho una vez que el paquete está listo en el mostrador, 
la cocina enviara una notificación directa al Proceso 4 que es ya directamente la aplicación del Repartidor. 
Este cuarto proceso recibe la instrucción, sincroniza su vector, y lanza su propio evento interno para 
calcular la ruta óptima de entrega mediante el GPS hacia el domicilio del cliente. 
Al iniciar el viaje, el repartidor actualiza el estado de la orden enviando un mensaje al último proceso.

Ya por ultimo, tenemos al Proceso 5 que es el servidor de notificaciones, donde en este al recibir el mensaje del 
repartidor, este ejecuta un evento interno para registrar el Tiempo Estimado de Llegada que es el ETA, y para acabar
el ciclo de la orden, el Proceso 5 emite un Broadcast hacia los cuatro procesos restantes P1, P2, P3 y P4 
indicando que la orden ha sido completada y entregada de forma exitosa. 

\newpage

Este ultimo paso es imortante, debido a que es el punto donde el sistema logra sincronizar completamente todos los estados
haciendo que los cinco relojes vectoriales sean los mismos de manera simultánea.


\textbf{Servicios gRPC}

\begin{enumerate}
  \item \textbf{Enviar Mensaje}: Recibe una estructura ReqEnvio con los identificadores de origen, 
  destino y de mensaje, esto de forma estructurada como una cadena, despues de esto se incrementa 
  la posición en el Reloj Vectorial del emisor y coloca la línea de envío en la bitácora.
  \item \textbf{Recibir Mensaje}: Recibe una estructura ReqRecepcion que contiene el proceso de origen, el mensaje
  y el arreglo del vector, depsues de esto actualiza el reloj local calculando los valores 
  máximos, esto por de forma que lo hace componente a componente, e incrementando en 1, por ultimo registra 
  el evento de recepción y devuelve un mensaje de confirmación con el vector del reloj con el tiempo actual.
  \item \textbf{Evento Interno}: Recibe una solicitud ReqInterno con la descripción de una tarea (armado de carrito, 
  validación de pago, preparación en cocina o cálculo de ruta GPS), despues este incrementa la posición 
  en su reloj lógico vectorial y pone de forma síncrona la entrada en el archivo de registro.
  \item \textbf{Broadcast}: Recibe una petición de difusión masiva, est emimso incrementa el reloj vectorial 
  del emisor en 1 y atiende de manera por igual al mismo tiempo el estado actual 
  junto con el mensaje a todos los demás procesos para sincronizar el estado de la orden.
\end{enumerate}

\subsection{Códigos docker:}

\textbf{Dockerfile:}

El archivo Dockerfile lo que hace es que define las instrucciones de como se ira 
contruyendo la imagen base de los contenedores. 

Para esto la primer alinea, lo que ahce es que inicia una imagen optimizada de Python python:3.11-slim, depsues de esto, 
establece /app como el directorio de trabajo principal dentro del entorno virtual. 

Despues de esto, transfiere el archivo de requerimientos e instala las dependencias 
mediante pip install, utilizando la bandera --no-cache-dir, esto se hace mas que nada 
para evitar almacenar archivos temporales y reduce el peso del contenedor final, despues de esto, 
copia los directorios de código que en neustro los tenemos por carpetas separadas, que son
proto y src, y configura la variable de entorno PYTHONPATH 
esto se hace para que el intérprete reconozca los módulos importados. 

No obstante en la 13 linea, tenemos lo mas importante, que es directaemtne el lanzamiento de 
el servidor gRPC, esto por medio de la compilacion inicial del archivo proto, este lo que hara es que
procesa el archivo procesos.proto para generar las clases cliente y servidor en Python.
 
Finalmente, declaramos el uso del puerto 50051 para permitir la comunicacion de el gRPC y 
definemos como comando por defecto la ejecución del servidor principal src/process.py.

\textbf{Docker Compose:}

El archivo docker-compose es el que se encarga de orgnizar directamente
toda la estrucutra completa del sistema, definiendo desde la red aislada 
y un total de seis servicios, donde en este caso son cinco procesos de procesamiento 
p1 a p5 y un proceso o nodo que es el cliente. 

Para cada uno de los procesos servidores, el codigo lo que hace, es que indica que la imagen debe 
construirse a partir del directorio actual y le asigna un nombre de contenedor, esto por medio del comando 
environment, despues de esto se colocan ya directamente las variables de entorno 
para la lógica del código en Python, que en este caso son las de los requesitos del proyecto, tales como
el identificador único del proceso PROCESS\_ID, el mapa de la red indicando las rutas de todos los nodos
y la ruta de destino para almacenar directametne las bitacoras. 

Para asegurar que los archivos generados no se pierdan al apagar los contenedores, 
se utiliza columentes directamente, que lo que hace es que, mapea un directorio local hacia dentro del propio contenedor. 

No osbante, el servicio cliente es casi igual, pero sobrescribe el comando de inicio por defecto con 
``sleep" e ``infinity", esto es por que lo que queremos es que mantenga en un estado de reposo 
para poder seguir mentiendo comandos de prueba, que son los \textbf{docker exec}. 

Finalmente, en la parte inferior del archivo, se define la red\_privada bajo un formato de tipo puente
con una subred que en este caso es parecido al usado directamtne en clase en los ejercicios, siendo para este proyecto 
el 172.21.0.0/16, lo cual permite usar direcciones estáticas para cada contenedor.

\subsection{Secuencia de comandos para el escenario esto, para la terminal 2}

\begingroup
\shorthandoff{"}

\textbf{1. P1 (App Cliente) -- Evento interno: crear el carrito}

Inicia el evento interno en P1 simulando que la app del cliente crea la orden. 

P1 incrementa su propia posición en el reloj vectorial, pasando de \texttt{[0,0,0,0,0]} a \texttt{[1,0,0,0,0]}. 

en este punto no hay comunicación con otros procesos.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P1 interno --desc "armar carrito pedido"
\end{quote}

\newpage

\textbf{2. P1 $\rightarrow$ P2 - solicitud de cobro}

P1 envía un mensaje gRPC punto a punto a P2 con los datos de la orden. 

Al enviarlo, P1 incrementa su reloj nuevamente y envia su vector al mensaje. 

Al recibirlo, P2 compara los vectores numero a nuemero del arreglo, 
toma los máximos e incrementa su propia posición.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P1 enviar --receptor P2 --msg '{"id":"ORD-77X", "total":250, "req":"cobro"}'
\end{quote}

\textbf{3. P2 (Verficiacion de Pago)}

P2 ejecuta un evento interno simulando que se verifica si tarjeta de crédito tiene fondos y es real. 

Solo incrementa su posición en el reloj vectorial.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P2 interno --desc "validar cobro tarjeta"
\end{quote}

\textbf{4. P2 $\rightarrow$ P3 - Confirmacion al restaurante}

Con el pago aprobado, P2 le envía los detalles de la orden a P3 vía gRPC. 

P3 recibe el vector de P2, aplica lo mismo de revisar los máximos e incrementa su propia posición. 

Su reloj ahora esta sincornizuado con los eventos previos de P1 y P2.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P2 enviar --receptor P3 --msg '\{"id":"ORD-77X", "pago":"ok", "item":"Super Star"\}'
\end{quote}

\textbf{5. P3 (Restaurante)}

P3 ejecuta un evento interno que lo que hace es que simula la preparación y que se empaqueta la hamburguesa. 
Su reloj vectorial avanza en su propia posición.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P3 interno --desc "preparar comida"
\end{quote}

\newpage
\textbf{6. P3 $\rightarrow$ P4 - Aviso al repartidor}

P3 envía un mensaje gRPC a P4 indicando que el paquete está listo para recolección. 

P4 combina directamente el vector recibido con el suyo, sincronizando su reloj con 
todos los eventos acuymulados.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P3 enviar --receptor P4 --msg '\{"id":"ORD-77X", "paquete":"listo"\}'
\end{quote}

\textbf{7. P4 (Repartidor) - Evento interno: calcular ruta GPS}

P4 realiza un evento interno que simula el cálculo de la ruta óptima hacia el destino del cliente mediante GPS. 

Solo incrementa su posición en el reloj vectorial.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P4 interno --desc "calcular ruta gps"
\end{quote}

\textbf{8. P4 $\rightarrow$ P5 -- Notificación de inicio de viaje}

P4 le comunica a P5 que es el sevidor de notificaciones que el repartidor ya está en camino. 

P5 recibe el vector con el historial completo de todos los procesos y lo combinad directamente con el suyo 
para preparar el broadcast.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P4 enviar --receptor P5 --msg '{"id":"ORD-77X", "repartidor":"va", "eta":"15m"}'
\end{quote}

\textbf{9. P5 (Servidor de Notificaciones)}

P5 ejecuta un evento interno para calcular y registrar el tiempo estimado de llegada 
antes de mandar el broadcast. 

Su reloj vectorial avanza en su propia posición.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P5 interno --desc "enviar notificacion"
\end{quote}

\textbf{10. P5 -- Broadcast final a todos los nodos}

P5 envía a todos al mimso tiempo el estado final de la orden a P1, P2, P3 y P4 mediante una difusión gRPC. 

Cada proceso receptor compara el vector actualizado de P5 con el suyo y termina con los tiempos acutlaizdos de forma correcta todos.

\begin{center}
  \textbf{Comando:}
\end{center}

\begin{quote}
\textcolor{blue}{docker} \textcolor{green}{exec} -it cliente python src/cli.py --destino P5 difusion --msg '\{"id":"ORD-77X", "fin":"entregado", "eta":"15m"\}'
\end{quote}

\subsection{Revision de logs:}

Para revisar el archivo de bitácora generado por cada nodo al finalizar la secuencia

\begin{quote}

creados:

\begin{quote}
\texttt{\textcolor{blue}{docker} compose down}
\end{quote}
